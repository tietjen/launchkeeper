# Contributing to launchkeeper

Thanks for looking under the hood. This project is small on purpose and has a
few rules that are not up for negotiation, because they are what keeps a tool
that deletes launch plists from becoming an `rm` wrapper.

## Build and test

```
swift build
swift test          # hermetic: no launchctl, no sfltool, no sudo, no real home
```

Requires Xcode 16 or later (Swift 6), macOS 14 or later. The universal
release build and signing live in `scripts/release.sh` (maintainer only).

## The rules

1. **Inventory and mutation never share a code path.** Scanners read; the
   remediation module reads the scan and mutates through planned, argv-only
   commands. A scanner that writes is a bug.
2. **Dry-run is the default, `--apply` is the only switch, and there is no
   bypass.** Do not add `--force`, `--yes` or anything that reaches past
   `RemediationGate`.
3. **Verify after mutate.** A change counts only when re-reading the system
   shows it. Tests that only assert an exit code are not enough.
4. **Unknown stays unknown.** Orphan and risk detection flag only provable
   facts (a missing file, a gone bundle). Absence of evidence is not evidence.
5. **Every operation is audited**, including refusals and dry-runs.

## Tests

- Everything goes through the `CommandRunner` seam; tests use scripted or
  stateful doubles (`FakeLaunchd`, `RemovalRunner`, `BTMStoreDouble`). The
  single exception spawns `/bin/sh` to pin the process-group behaviour of the
  interactive seam.
- **Fixtures are synthetic.** `Tests/Fixtures/*.txt` are anonymized captures
  regenerated by `scripts/anonymize-fixtures.py` from real ones in
  `Tests/Fixtures/real/` (git-ignored, never committed). Never add a capture
  that contains a hostname, a user name or a real application inventory.
- A live drill against your own Mac is welcome as *manual* verification, but
  it is not a test and must not be automated.

## Pull requests

- One change per PR, with a test that fails without it.
- Keep the design guarantees above intact; if a change needs to weaken one,
  open an issue first and explain why.
- Update `CHANGELOG.md` under *Unreleased*.
- Code and comments are in English; commit messages say what changed and why.

## Releases (maintainer)

`scripts/release.sh <version> --notarize --upload` runs the tests, builds the
universal binary, signs it with the Developer ID certificate, notarizes it and
publishes the tarball plus `SHA256SUMS`. The version must match
`Sources/launchkeeper/LaunchKeeper.swift` and `BackupEnvironment.toolVersion`.
